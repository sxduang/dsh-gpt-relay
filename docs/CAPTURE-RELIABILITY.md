# 截图可靠性与输入保护修复

2026-11-01。项目 <repo>。

## 核实的问题

日志中的 29ba389b 确认有 Error: answer-layout-changed；ad20350e 的截图实际上已成功生成，但被回答包含原图时跳过截图的旧投递规则省略。旧 CLI 又固定宣称截图已经发送，造成错误预期。

中转源码没有发现右键“检查”、F12 或打开 DevTools 的操作，开发者工具面板弹出的直接来源尚未确认。本轮没有把这一现象武断归因于某个工具。

## 改动

- 所有正常回答有截图时都发送，包括短回答和带原图的回答。静默模式仍只保存，不投递。
- 截图前等待字体和图片资源（有时间上限）、关闭临时动画/过渡，并连续检查稳定布局。
- 截图后检测到布局变化时丢弃该帧，重新测量和整图捕获，最多 4 次。继续使用单张原生长截图，不回到滚动分片，也不重新向 GPT 提问。
- 最终失败包含尝试记录。发送的第一条文字明确提示截图未送达，不悄悄省略。
- 检查微信发送器退出码：截图已保存与已发出分开记录。状态接口新增 delivery，包含 status、screenshotSent、screenshotFile、screenshotError、errors。CLI 等待投递结束再报告结果，不再固定说截图已发送。
- 页面临时样式有 finally 恢复和 25 秒自动恢复定时器；调试器中途断开时也有恢复途径。
- 正式输入、dryrun 和点击发送前检查该标签页的调试器占用；被占用时停止，不盲目输入。写入文字前确认焦点位于输入框。代码不会打开、切换或强制关闭用户的 DevTools。
- 更新项目与实际微信工作区的 DSH 操作约定：用中转诊断接口排查，禁止右键检查/F12/控制台补救；done 不等于截图投递成功。

调试器占用检查依据 Chrome debugger.getTargets 的 attached 字段：
https://developer.chrome.com/docs/extensions/reference/api/debugger#type-TargetInfo

## 验证与边界

自动化测试覆盖短回答/自带图均发截图、发送器失败仍保留文字、截图失败提示、CLI 不作虚假确认、等待投递完成、调试器占用和焦点失败保护。

真实本机 Chrome 测试在 125% 像素密度下，故意在截图瞬间改变回答高度：第一次截图被丢弃，第二次正确生成新高度的整图；每次都变化时恰好尝试四次后返回失败，并恢复页面。长图连续性、图片上传和原有接口回归也纳入检查。

未向真实微信发送测试消息，也未对用户正在登录的 ChatGPT 页面做本轮自动操作。调试器占用检查不能识别是谁打开了面板，已打开的其他调试器不会被强制关闭。
