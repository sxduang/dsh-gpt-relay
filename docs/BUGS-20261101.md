## 缺陷 A（高）：拼接接缝处出现文字重影 / 半截字

**现象**：两片拼接的交界处，有一整行文字被水平切开并轻微错位，肉眼可见一条「半截字 + 重影」的横带。

**证据**
- 任务 `118d88d1`（1632 字，1 个表格，2 片）
- 截图：`<repo>\.gpt-relay\sessions\session-shot-1\media\118d88d1\answer.png`（1055×1668 像素，dpr 1.25）
- 接缝位置：图片纵向约 **y≈730px**（CSS ≈584px）处，正好落在「第一步：数据读取…….」这一行的中间
- `screenshotInfo`：`{height:1334, width:844, contentHeight:1258, padding:38, complete:true, dpr:1.25, slices:2}`

**相关代码**
- `extension/src/background/capture.mjs:108-113`：先 `place(offset - 32)`，再用 `settled()` 实测 `state`，然后
  `start = Math.max(offset, Math.ceil(state.viewTop - state.top))`、`end = Math.min(total, Math.floor(state.viewBottom - state.top))`
- `extension/src/background/capture.mjs:122-126`：裁切用
  `sx = round(left*dpr)`、`sy = round((top+start)*dpr)`、`sh = round(end*dpr) - round(start*dpr)`
- `extension/src/background/capture.mjs:118`：坐标变化 >0.5 就丢弃重拍

**怀疑原因**（未改代码，仅推断）
1. `start/end` 用 `ceil/floor` 取整到 CSS 整像素，而裁切时又各自 `Math.round(…*dpr)`；dpr=1.25 时同一坐标会出现 1px 级不一致，接缝处切在字形中间。
2. `viewTop` 取的是滚动容器的 `rect.top`，但容器顶部可能压着高度不为 0 的 sticky 头部（虽然已被 `visibility:hidden`，几何仍在），`viewTop - top` 与实际「首次可见内容坐标」差了几像素。
3. `settled()` 只要求连续两帧坐标差 <0.5，滚动惯性停止但亚像素仍在缓慢变化时可能提前判定稳定。

**建议方向**：所有坐标统一到设备像素再计算（先 `×dpr` 后取整，`start/end` 用同一套取整规则）；接缝处改为「按实测重叠量裁掉，且重叠量下限 ≥ 8 CSS px」，避免 1~2px 的浮点误差直接切字；或改为按行边界对齐（用接缝附近文本行的 `getClientRects()` 吸附）。

## 缺陷 B（高）：末尾内容丢失，但 `complete: true`

**现象**：`.md` 原文最后一段「总结：这 8 步构成了从原始数据到生物学解释的完整分析框架……」在截图里**完全没有**，最后一行还被切掉半截；但 `screenshotInfo.complete` 报 `true`，调用方据此认为截图完整。

**证据**
- 同一任务 `118d88d1`，原文 `<repo>\.gpt-relay\sessions\session-shot-1\118d88d1.md`（1632 字符，结尾为「总结：……」整段）
- 截图末尾只到「第八步：差异表达与功能富集……」段落结束，下面直接是留白
- `screenshotInfo.height=1334`、`contentHeight=1258`、`padding=38`，即 `1258 + 38×2 = 1334`，说明循环是在 `offset` 达到 `info.height` 时正常退出的

**相关代码**
- `extension/src/background/capture.mjs:48`：`height` 在 `prepare` 阶段一次性测得（`Math.ceil(r.height)`）
- `extension/src/background/capture.mjs:98`：`total = Math.min(info.height, 24000, 画布预算)`
- `extension/src/background/capture.mjs:132`：`if (offset < info.height) return capture-incomplete`
- `extension/src/background/capture.mjs:144`：`complete: offset >= info.height`

**怀疑原因**：`prepare` 发生在还没滚动过的时刻，此时虚拟列表只挂载了视口附近的内容，元素 `getBoundingClientRect().height` 偏小（本例 1258，实际正文更高）。后续所有裁切都以这个偏小的 `total` 为上界，于是「完整」判定天然成立——**用测量值当真相，而不是用实际滚动到的位置**。

**建议方向**：`total` 不应作为完成判据。改为：滚到滚动容器真正到底（`scrollTop` 不再变化）后，再实测元素底边与当前视口的关系；只有「元素底边已进入视口且已绘制」才算 complete。另外末尾建议多留 1 个行高（约 24px）的余量，避免最后一行被视口底边切半。

## 缺陷 C（中）：长回答任务跑到 360s 超时，无任何中间回传

**现象**：3000 字 + 2 表格的任务排队后一直无结果，358s 时被 worker 判 `timeout`，微信收到超时提示；期间内容脚本既没回传错误，也没有阶段日志，无法判断卡在生成还是截图。

**证据**
- 任务 `5bc01456`，日志 `<repo>\relay\relay.log`：
  - `05:58:37 job queued … newChat:true`
  - `05:58:39 job taken {"tab":"https://chatgpt.com/c/6ae6d4dd-…"}`
  - `06:04:37 job timeout`
  - 无任何 `job done` / `wechat-send`（除了超时提示）
- 页面侧：用户确认「新对话开了、问题发出去了、GPT 已经答完」
- 轮询在 `06:04:53` 恢复（`health.lastTabSeen`），说明内容脚本当时刚从 `busy` 状态退出，即整个 `handle()` 一直跑到超时前后才结束

**相关代码**
- `extension/src/content/shared.mjs:2`：`ANSWER_WAIT_MS = 300000`（等待回答上限 300s）
- `extension/src/content/ask.mjs:83`：`waitAnswer(Date.now() + ANSWER_WAIT_MS, …)`
- `extension/src/content/ask.mjs:107`：随后才 `screenshotNode(...)`
- `relay/config.json:8`：`"jobTimeoutSec": 360`
- `extension/src/content/runtime.mjs:71`：`if (busy) return`（`busy` 期间不再轮询，所以 worker 端看不到任何中间状态）

**判断**：`300s 等待上限 + 截图耗时` 与 `360s 任务超时` 只差 60s 余量，长回答必踩线；而且失败时**第一个被丢掉的恰是诊断信息**——内容脚本算出的 `no-answer` / `timedOut` 结果因为任务已超时被 worker 丢弃，用户只看到「超时」。

**建议方向**
1. 调整余量：`jobTimeoutSec` ≥ `ANSWER_WAIT_MS` + 截图预算（建议 600），或把 `ANSWER_WAIT_MS` 降到 240 并让任务超时 480。
2. 阶段回传：`typed` / `sent` / `answer-started` / `answer-finished` / `capture-start` / `capture-done` 各上报一次轻量事件（不落盘，只进日志与 `job.meta`），这样「卡在哪一步」不再靠猜。
3. 内容脚本侧也应监听任务是否已被判超时（例如 `/result` 返回 `job-inactive` 时停止继续截图），避免做无用功。

## 验收标准（建议写进回归）

1. 一张 3000–6000px 的长图：**接缝处任意一行文字不得出现重影、半截或 1px 错位**（可用一行含下划线的文字做基准目视检查）。
2. 截图内容必须覆盖 `.md` 的最后一段；`complete` 只有在「滚动容器已到底且元素底边已绘制」时才为 `true`，否则返回 `capture-incomplete`。
3. 长任务的时间预算：`jobTimeoutSec` 至少比「等待回答上限 + 截图耗时」多 120s；超时前必须能在日志里看到最后一次阶段事件。
4. 失败路径仍保持现有行为：文字先发、错误原因 + 现场视口截图随后。
